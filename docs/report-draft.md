## Вступ

Мета практики — розробити серверну частину застосунку для створення, упорядкування та пошуку нотаток. Обрано тему «Менеджер нотаток із категоріями та пошуком». Частина 2 охоплює серверну реалізацію: REST API, збереження даних у базі, керування залежностями, middleware та документацію API.

Проєкт містить три ресурси: нотатки, категорії та теги. Користувач може створювати й редагувати нотатки, призначати категорії та кілька тегів, а також фільтрувати нотатки за текстом, категорією і тегом.

Для порівняння розглянуто відкриті системи для нотаток, документація або вихідний код яких описують серверну архітектуру.

| Система | Сервер, API і зберігання | Висновок для проєкту |
|---|---|---|
| Joplin Server | Серверна програма на Node.js надає REST API. Типове виробниче розгортання використовує PostgreSQL для метаданих і може зберігати вміст у БД, файловій системі чи S3; SQLite доступна для тестового й локального запуску [1; 2]. | Підтверджує доречність Node.js і REST API для роботи з нотатками. Для навчальної версії достатньо SQLite без окремої інфраструктури. |
| Trilium Notes | Сервер зберігає нотатки та зв’язки в SQLite через `better-sqlite3`. | Standard Notes | Самостійне розгортання складається з API Gateway, сервісів синхронізації й автентифікації, фонових процесів, бази даних та Redis-кешу. | Umzug | Запуск і облік версійованих міграцій схеми БД. |

### 2.2 Специфікація вимог та архітектура

### 3.1 Функціональні вимоги

1. API має надавати CRUD-операції для нотаток, категорій і тегів.
2. Нотатка має назву та текст, може належати категорії й мати кілька тегів.
3. Категорія може містити багато нотаток; зв’язок нотаток і тегів є «багато до багатьох».
4. Список нотаток має підтримувати пошук за назвою або текстом і фільтри за категорією та тегом.
5. API має повертати зрозумілі помилки для некоректних даних і неіснуючих ресурсів.
6. Swagger UI має описувати доступні маршрути та формати даних.

### 3.2 Нефункціональні вимоги

- Код поділений на маршрути, контролери, сервіси й репозиторії.
- Запити перевіряються до виконання операцій з базою даних.
- Помилки обробляються централізовано, запити й ключові операції журналюються.
- Конфігурація винесена у змінні середовища, локальна база й `.env` не додаються до Git.
- База даних створюється і змінюється міграціями.

### 3.3 Архітектура

```text
Клієнт (Postman / Swagger UI)
              |
              v
Express middleware: CORS, JSON, Morgan, валідація, помилки
              |
              v
Маршрути -> Контролери -> Сервіси -> Репозиторії
                                         |
                                         v
                                  Sequelize ORM
                                         |
                                         v
                                      SQLite
```

DI-контейнер Awilix створює й передає залежності сервісам та репозиторіям. Схема БД складається з таблиць `notes`, `categories`, `tags` і проміжної `note_tags`.

## Розділ 3. Розробка застосунку

Сервер побудовано на Express. Маршрути `/api/notes`, `/api/categories` і `/api/tags` надають отримання списку й окремого запису, створення, оновлення через PUT/PATCH та видалення. Для нотаток доступні параметри пошуку `q`, `categoryId` і `tagId`.

PUT замінює ресурс повністю, а PATCH змінює тільки передані поля. Під час заміни нотатки відсутні `categoryId` і `tagIds` скидаються; для категорії відсутній опис очищується.

ORM-моделі описують три сутності та їхні зв’язки. Міграція створює таблиці, зовнішні ключі й індекси. Репозиторії інкапсулюють запити Sequelize, сервіси реалізують перевірку пов’язаних сутностей і бізнес-операції, контролери перетворюють HTTP-запити на виклики сервісів. Swagger UI доступний за адресою `/api-docs`.

**Місце для рисунків:** структура проєкту; приклад моделі та міграції; запуск Swagger UI; приклади створення й пошуку нотатки.

## Розділ 4. Тестування та технічна документація

Для перевірки підготовлено Postman-колекцію `postman/notes-manager.postman_collection.json` і автоматизований HTTP smoke-тест `scripts/smoke-test.js`. Перевірку виконано 10.10.2026 у Windows із Node.js 24.19.0 командою `pnpm test:smoke`: усі 29 перевірок пройшли.

| Сценарій | Очікуваний результат | Фактичний результат |
|---|---|---|
| Створення нотатки з наявними категорією і тегом | HTTP 201, повертається створений запис | Пройдено, HTTP 201 |
| Пошук за текстом і фільтрами | HTTP 200, повертається відповідний список | Пройдено для тексту, категорії й тегу |
| Порожня назва нотатки | HTTP 400 з описом помилки валідації | Пройдено, HTTP 400 |
| Назва нотатки з максимально дозволених 160 символів | HTTP 201 | Пройдено, HTTP 201 |
| Назва нотатки завдовжки 161 символ | HTTP 400 | Пройдено, HTTP 400 |
| Некоректний ID | HTTP 400 | Пройдено, HTTP 400 |
| Коректний, але відсутній ID | HTTP 404 | Пройдено, HTTP 404 |
| Повний CRUD кожного ресурсу | Створення, читання, оновлення й видалення виконуються очікувано | Пройдено для нотаток, категорій і тегів |

Під час першого запуску HTTP-перевірки виявлено, що міграція не знаходила файл у Windows через формат шляху з `\`. Шлях міграцій нормалізовано до `/`; після повторного запуску створилися всі таблиці, і сценарії пройшли. Також pnpm 11 не запускав скрипт встановлення `sqlite3`, тому додано явний дозвіл на цей потрібний скрипт у `pnpm-workspace.yaml`.

**Місце для скриншотів:** відкрити Swagger UI за адресою `http://localhost:3000/api-docs` або запустити колекцію в Postman і вставити скриншоти фактичних запитів та відповідей.
